![AIにコードを書かせるほど、エンジニアは「設計」が仕事になる](https://raw.githubusercontent.com/Inosuke0718/Zenn/main/images/ai-coding-engineering-design/hero.png)

最近、AIを使って開発するうえで、自分なりにかなり意識していることがあります。

今回はそれを少し紹介させてください。

Claude CodeやCodexのようなコーディングエージェントを使っていると、以前と比べて「コードを書く」という作業そのものにかかる時間が、かなり減ってきました。

以前なら、機能を一つ追加するだけでも、

- 既存コードを読む
- 実装方法を考える
- コードを書く
- エラーを調べる
- 修正する
- テストする

といった作業に、それなりの時間がかかっていました。

今は、要件さえある程度整理できていれば、AIが既存コードを調査し、実装方針を考え、コードを書き、テストまで進めてくれる場面が増えています。

そんな中で、最近自分が特に意識しているのが、

**「AIにどうコードを書かせるか」よりも、「AIが正しく動けるように、こちらがどう開発を設計するか」**

ということです。

AIが優秀になればなるほど、

**「コードを書く速度」は、開発速度を決める一番の要因ではなくなっていく**

ように感じています。

その代わりに重要になってくるのが、

- そもそも何を作るのか
- どんな構造で作るのか
- AIにどこまで任せるのか
- 出てきた成果物をどう評価するのか

といった部分です。

この記事では、最近自分がAIを使った開発で意識していることをベースに、AI時代のエンジニアリングがどう変わっていくのか、自分なりの考えを整理してみます。

## 「AIにコードを書かせる」だけでは、あまり変わらない

AIコーディングというと、最初はこういう使い方をしがちです。

```text
ログイン機能を作ってください
```

あるいは、

```text
このエラーを直してください
```

もちろん、これだけでも便利です。

ただ、この使い方ではAIは基本的に、

**「高速なコーディング補助ツール」**

のままです。

AIエージェントの本当の面白さは、コードを書くことだけではありません。

例えば、

```text
まず関連するコードを調査してください。

今回の変更による影響範囲を洗い出し、
実装方法を3案考えてください。

それぞれのメリット・デメリットを比較したあと、
最も安全な方法で実装計画を作ってください。

まだコードは変更しないでください。
```

と指示すると、AIの役割が一気に変わります。

単なるコード生成器ではなく、

**「開発プロセスに参加するエンジニア」**

に近くなります。

そして個人的には、AIコーディングで最も重要なのは、この使い方の変化だと思っています。

## 実装する前に、考えさせる

AIを使った開発で、かなり重要だと思っている原則があります。

それが、

**「いきなり実装させない」**

ことです。

例えば新しい機能を作るなら、

```text
要件整理
↓
既存コード調査
↓
影響範囲確認
↓
設計
↓
実装計画
↓
実装
↓
テスト
↓
レビュー
```

という順番で進めます。

人間の開発でも当たり前に見える流れですが、AIを使うとつい、

```text
これ作って
```

から始めてしまいます。

そしてAIは非常に素直なので、それらしい実装をすぐ作ってくれます。

問題は、

**「動くコード」と「良いコード」は別物**

だということです。

AIは要求された局所的な問題を解くのは非常に得意です。

一方で、

- このプロジェクトではどんな設計思想を採用しているのか
- 半年後にも変更しやすい構造なのか
- 他機能との責務が混ざっていないか
- 本当にその機能自体が必要なのか

といった判断は、まだ人間側でかなりコントロールする必要があります。

だからAI時代ほど、

**実装前の設計が重要になる**

と感じています。

## AIが優秀になるほど「曖昧な設計」が危険になる

AIにコードを書かせていると、意外とすぐに起きる問題があります。

それが、

**コードベースの一貫性が崩れること**

です。

例えばプロジェクトに、

```text
services/
utils/
helpers/
lib/
common/
```

のようなディレクトリがあるとします。

人間でも、

> この処理はserviceなのか？

> utilなのか？

> libなのか？

と迷うことがあります。

当然、AIも迷います。

するとセッションごとに、

```text
今回は service に実装
次は utils に実装
別のAIは lib に実装
```

ということが起きます。

一つ一つは間違っていなくても、半年後には、

**「似た処理がいろいろな場所にあるコードベース」**

が完成します。

## AI時代の設計は「AIが迷わない設計」

ここで重要になるのが、アーキテクチャです。

DDDでもクリーンアーキテクチャでもFeature-Sliced Designでも、何でもいいと思っています。

重要なのは名前ではありません。

**「どの責務をどこに置くのかが明確であること」**

です。

例えば、

```text
domain
  ├─ Entity
  ├─ ValueObject
  └─ DomainService

application
  ├─ UseCase
  └─ ApplicationService

infrastructure
  ├─ Repository
  └─ ExternalAPI

presentation
  └─ Controller
```

というルールがあれば、AIも、

```text
DBアクセス
→ infrastructure

業務ルール
→ domain

ユースケース
→ application
```

と判断しやすくなります。

つまり、AI時代の良いアーキテクチャには、

**人間が理解しやすい**

だけではなく、

**AIが迷いにくい**

という新しい価値が加わったのではないかと思っています。

## CLAUDE.mdやAGENTS.mdは「AI向けREADME」ではない

Claude Codeなら`CLAUDE.md`、Codex系の環境なら`AGENTS.md`など、AIにプロジェクトルールを渡す仕組みがあります。

これらを単なる、

**「AI用のREADME」**

として扱うのは少しもったいないと思います。

ここには、

```markdown
## Architecture

- UIから直接DBへアクセスしない
- Domain層はInfrastructure層に依存しない
- 外部APIアクセスはRepository経由とする

## Development Flow

1. 実装前に関連コードを調査する
2. 影響範囲を説明する
3. 実装計画を作る
4. 必要なテストを追加する
5. lint / test / buildを実行する

## Coding Rules

- anyは禁止
- 型定義を優先する
- 既存パターンを優先する
- 新しいライブラリ追加前に確認する
```

のように、

**「このチームではどう考えて開発するのか」**

まで書いておく。

そうするとAIは単にコードを書くのではなく、

**チームの開発ルールの中で仕事をする**

ようになります。

AI時代では、こうしたルールを文章化する能力自体が、かなり重要になる気がしています。

## エンジニアは「コードを書く人」から「AIをレビューする人」になる

AIが実装を担当できるようになると、エンジニアの仕事は減るのでしょうか。

個人的には、

**減る部分と、増える部分がある**

と思っています。

確実に減るのは、

- ボイラープレートを書く
- APIの型を調べる
- CRUDを書く
- 単純なリファクタリングをする
- 似たコードを量産する

といった仕事です。

一方で増えるのが、

- 要件を整理する
- 設計を決める
- AIの実装をレビューする
- テスト観点を考える
- セキュリティを確認する
- 本番運用を考える

といった仕事です。

つまり、

```text
実装者
```

から、

```text
設計者
+
レビュアー
+
意思決定者
```

へ少しずつ役割が移っていく。

## 「AIが書いたコードを読めない」はかなり危険

AI時代だからプログラミングを勉強しなくてもよくなる、という意見もあります。

これについては、少なくとも現時点では逆だと思っています。

AIが大量のコードを書けるようになるほど、

**大量のコードを短時間で評価する能力**

が必要になります。

例えばAIが、

```text
認証処理を変更しました。
```

と言ってきたとします。

そのとき、

- 認可漏れはないか
- セッション管理は安全か
- 既存ユーザーへの影響はないか
- APIの公開範囲は正しいか

を判断できなければ、AIのコードをそのまま信用するしかありません。

それではかなり危険です。

AIによって、

**コードを書く能力の価値が下がる**

可能性はあります。

しかし、

**コードを理解する能力の価値まで下がるわけではない**

と思っています。

むしろレビューするコード量が増える分、読む能力はさらに重要になるかもしれません。

## 開発速度が上がると、ボトルネックは「実装」ではなくなる

これがこの記事で一番書きたかったことです。

以前の開発では、

```text
アイデア
↓
要件定義
↓
設計
↓
実装 ← ここが重い
↓
テスト
```

というケースが多くありました。

しかしAIによって実装コストが大幅に下がると、

```text
何を作る？
↓
なぜ作る？
↓
誰が使う？
↓
どう設計する？
↓
本当にこれでいい？
```

という部分の比重が上がります。

つまりボトルネックが、

**How to build**

から、

**What to build / Why to build**

へ移っていきます。

## AI時代に強いのは「コードが速い人」ではなく「問題を正しく切れる人」

例えばユーザーから、

> CSVをアップロードできる機能が欲しい

と言われたとします。

以前なら、

```text
CSVアップロード機能
↓
実装
```

となるかもしれません。

でも本当に解決したい問題を聞くと、

> 毎週Excelで管理している顧客データをシステムに登録するのが面倒

なのかもしれません。

そうすると解決策は、

- CSVアップロード
- Google Sheets連携
- Excelファイル直接読み込み
- API連携
- RPA
- データ同期

など、いろいろ考えられます。

AIは、

**与えられた問題を高速に解く**

のは非常に得意です。

一方で、

**そもそも解くべき問題は何なのか**

を決めるのは、まだ人間の重要な仕事です。

だからAI時代ほど、

- ヒアリング
- 業務理解
- 課題発見
- 要件定義

の価値が上がると思っています。

## 「働くほど仕事が減る」開発を目指したい

AIを使っていて、個人的に一番面白いと思う考え方があります。

それが、

**同じ仕事を2回しない**

という考え方です。

例えば毎週、

```text
データをダウンロード
↓
Excelで加工
↓
メールを作成
↓
顧客へ送信
```

という作業があるとします。

従来なら、

> この作業を効率よくやる方法

を考えるかもしれません。

でもAIを使えるなら、

> この作業そのものをなくせないか？

と考えられます。

```text
データ取得
↓
自動集計
↓
AIが文章生成
↓
自動送信
```

まで作れば、次回から人間は作業する必要がありません。

つまり、

```text
仕事をする
↓
面倒な部分を見つける
↓
自動化する
↓
次からやらなくていい
```

という循環です。

AI時代のエンジニアは、

**仕事を処理する人**

ではなく、

**仕事そのものを消していく人**

になれるのではないかと思っています。

## 一人のエンジニアが「小さな開発チーム」になる

さらに面白いのが、AIエージェントを並列に動かせることです。

例えば、

```text
Agent A
→ 認証機能

Agent B
→ 管理画面

Agent C
→ テスト

Agent D
→ ドキュメント
```

という形で複数のタスクを同時に進めることができます。

そうなると人間は、

```text
エンジニア
```

というより、

```text
Tech Lead
↓
AI Agent
AI Agent
AI Agent
AI Agent
```

に近い立場になります。

もちろん現実にはコンフリクトや設計の不整合も起きます。

だからこそ、

- タスクを適切に分割する
- 境界を決める
- 成果物をレビューする
- 全体の整合性を保つ

という能力が必要になります。

面白いことに、これはかなり、

**マネジメント**

に近い仕事です。

AIコーディングが進化すると、エンジニアリングとマネジメントの境界も少し曖昧になっていくのかもしれません。

## AIに任せる範囲は「実装」だけでなくていい

AIエージェントを使っていると、コーディング以外にも使えることに気づきます。

例えば、

```text
ユーザーインタビュー
↓
文字起こし
↓
要約
↓
課題抽出
↓
Issue生成
↓
実装
↓
テスト
```

までつなげることもできます。

あるいは、

```text
問い合わせ
↓
内容分析
↓
バグ判定
↓
GitHub Issue作成
↓
原因調査
↓
修正案作成
```

という流れも考えられます。

そうなると、

**AIコーディング**

という言葉自体が、少し狭いのかもしれません。

本当に起きているのは、

**ソフトウェア開発プロセスそのものの自動化**

です。

## それでも、人間が最後に持つべきもの

AIにかなりの作業を任せられるようになっても、最後まで人間側に残るものがあります。

それが、

**責任**

です。

AIが、

> テストはすべて通りました。

と言っても、

本番障害が起きたときに、

> Claudeが書いたので分かりません。

では済みません。

だから人間は、

- なぜこの設計なのか
- なぜこの実装なのか
- どんなリスクがあるのか
- どこまでテストしたのか

を説明できる必要があります。

AIがコードを書く時代でも、

**設計判断の責任までAIに渡せるわけではない**

ということです。

## まとめ

AIコーディングによって、エンジニアの仕事はなくなるのか。

自分は少し違うと思っています。

なくなっていくのは、

**「コードを書くこと自体が仕事だった部分」**

です。

その代わりに、

```text
課題を見つける
↓
要件を定義する
↓
設計する
↓
AIへ仕事を渡す
↓
レビューする
↓
テストする
↓
改善する
```

という部分が、より重要になっていく。

AI時代のエンジニアは、

**一番たくさんコードを書く人**

ではなく、

**一番うまく開発を設計できる人**

になっていくのかもしれません。

そして個人的には、その変化はかなり面白いと思っています。

コードを書く時間が減った分、

**「何を作るべきか」**

に、もっと時間を使えるようになるからです。

AIに実装を任せられる時代だからこそ、

エンジニアリングの本質は、むしろ以前より見えやすくなっているのかもしれません。
